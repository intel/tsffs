# Spec: AFL++-compatible campaign statistics

<!-- markdownlint-disable MD013 -->

## Problem Statement

A user running a TSFFS campaign has no standard way to watch it. Progress is only visible as a prose status line on the Simics console and as proprietary JSON records in `log.json`, which no tool outside TSFFS understands and which carry little beyond execution counts. Users who already monitor fuzzers with `afl-whatsup` and `afl-plot`, or who track campaigns in their own dashboards, cannot point that tooling at TSFFS. Campaigns run for days, often several in parallel on one host or a CI farm, so this blind spot costs real triage time: operators cannot tell at a glance whether an Instance is alive, still finding Edges, stable, or stuck.

The console line does not help either: it often goes quiet for long stretches. TSFFS drives LibAFL with `fuzz_one` directly and never calls `maybe_report_progress`, so LibAFL never emits periodic execution-stat events. `SimpleMonitor` therefore prints only when a new testcase or objective is found, and its output is relayed only at the next simulation stop. Once coverage plateaus, the console stops reporting.

The first implementation attempt also showed what not to do: a LibAFL `Monitor` only sees aggregated event counters, so most AFL fields were zero-filled or hard-coded, coverage counted Branch targets instead of Edges, and an I/O error while writing stats could abort the whole Simics session.

## Solution

Every TSFFS session maintains an Instance directory, `<output_directory>/<instance_name>/`, containing AFL++-format `fuzzer_stats`, `plot_data`, and `fuzzer_setup` files that stay current while the campaign runs. The values mean what AFL++ users expect them to mean, so `afl-whatsup` summarises a TSFFS campaign and `afl-plot` charts it without modification, and any script that parses AFL stat files works too.

On the same wall-clock cadence, TSFFS prints a one-line status summary to the Simics console, so interactive users get fresh feedback even when nothing new is being found.

Writing stats can never stop fuzzing. Two live sessions can never share an Instance, and restarting into an existing Instance never mixes two sessions into one graph.

This is the first stage of retiring `log.json` in favour of community-standard outputs (see ADR 0001): heartbeat and prose stats records stop being written to `log.json`, while its remaining records stay until their replacements land.

## User Stories

1. As a fuzzing operator, I want each TSFFS session to write an AFL++ `fuzzer_stats` file, so that I can inspect a campaign's state with the same tools I use for AFL++.
2. As a fuzzing operator, I want `afl-whatsup` to summarise all TSFFS Instances under one output directory, so that I can check a fleet of parallel campaigns with one command.
3. As a fuzzing operator, I want `afl-plot` to render a TSFFS Instance's `plot_data`, so that I can see coverage and corpus growth over time.
4. As a fuzzing operator, I want `edges_found` to count Edges (occupied coverage-map slots), so that the number is comparable with what AFL++ reports.
5. As a fuzzing operator, I want `bitmap_cvg` to be the share of the coverage map occupied by Edges, so that I can tell when coverage plateaus or the map nears saturation.
6. As a fuzzing operator, I want `bitmap_cvg` never to exceed 100%, so that I can trust it.
7. As a fuzzing operator, I want Edge counts reported even when coverage reporting is disabled, so that AFL stats do not depend on an unrelated setting.
8. As a fuzzing operator, I want `stability` computed as AFL++ does (unstable Edges relative to filled Edges), so that genuine non-determinism in the target is visible rather than hidden near 100%.
9. As a fuzzing operator, I want `stability` to reflect calibration results instead of a hard-coded value, so that I can detect timer- or interrupt-dependent paths the snapshot does not pin down.
10. As a fuzzing operator, I want `cycles_done` and `cycles_wo_finds` to report completed passes over the corpus and passes since the last find, so that I know how thoroughly the corpus has been explored and whether it has gone stale.
11. As a fuzzing operator, I want `pending_total` and `pending_favs` to report corpus entries not yet fuzzed, so that I can judge whether a campaign still has work queued.
12. As a fuzzing operator, I want `corpus_count` and `edges_found` to be current at every write, so that growth is not reported late even when a fuzzing round takes minutes.
13. As a fuzzing operator, I want `cur_item` and `max_depth` to reflect the fuzzer's real position and lineage depth, so that the stats are not misleading placeholders.
14. As a fuzzing operator, I want `saved_crashes` and `saved_hangs` reported separately, so that I can tell crashes from timeouts without opening the solutions directory.
15. As a fuzzing operator, I want `last_find`, `last_crash`, and `last_hang` to carry real timestamps, so that `afl-whatsup` can tell me how long since the last progress.
16. As a fuzzing operator, I want `execs_done` and `execs_per_sec` to be live at every write, so that throughput is never minutes stale.
17. As a fuzzing operator, I want `execs_ps_last_min` computed over the actual time since the previous write, so that slow iterations do not inflate the recent speed.
18. As a fuzzing operator, I want `execs_since_crash` to count executions since the most recent crash, so that it means what AFL++ users expect.
19. As a fuzzing operator, I want `exec_timeout` to reflect the configured TSFFS timeout, so that the file describes the real campaign settings.
20. As a fuzzing operator, I want stats written on a wall-clock cadence that I can configure with `afl_stats_interval`, so that the files stay fresh regardless of how long one fuzzing round takes.
21. As a fuzzing operator, I want a final stats write when the session shuts down, so that the last numbers on disk match the end of the campaign.
22. As an interactive Simics user, I want a one-line status summary (executions, executions per second, Edges, corpus size, crashes, hangs, time since last find) printed to the Simics console at every stats write, so that the console keeps reporting progress even when nothing new is found.
23. As an interactive Simics user, I want the fuzzer's existing new-testcase and objective lines to keep appearing on the console, so that I still see finds as they happen.
24. As a fuzzing operator, I want AFL stats enabled by default, so that every campaign is observable without extra configuration.
25. As a fuzzing operator, I want to disable AFL stats with one attribute, so that I can turn them off on hosts where writing extra files is unwanted.
26. As a fuzzing operator, I want to choose the output directory, so that I can put Instances on fast or shared storage.
27. As a fuzzing operator, I want the Instance to be named `default` unless I name it, as AFL++ does, so that repeated repro and debugging sessions reuse one directory instead of littering the output directory.
28. As a fuzzing operator running sessions in parallel, I want a second live session that targets an Instance already in use to fail at startup with an error telling me to set `instance_name`, so that parallel sessions never corrupt each other's stats.
29. As a fuzzing operator, I want a lock left by a crashed Simics process never to block the next session, so that I never have to clean up by hand.
30. As a CI maintainer, I want to set an explicit Instance name, so that each CI job's stats land in a predictable place.
31. As a CI maintainer, I want an Instance name containing anything other than letters, digits, `.`, `_`, and `-` (or consisting only of dots) to be rejected at startup with a clear error, so that stats never escape the output directory and `afl-whatsup` parsing never breaks.
32. As a CI maintainer reusing an Instance name, I want the previous session's `plot_data` preserved under a timestamped name when a new session starts, so that two sessions are never mixed into one graph and no history is lost.
33. As a CI maintainer, I want `fuzzer_stats` replaced atomically, so that a reader polling it never sees an empty or half-written file.
34. As a fuzzing operator, I want a stats write failure (full disk, read-only share, Windows file-sharing lock) to log a warning and let fuzzing continue, so that a multi-day campaign is never lost to a monitoring side feature.
35. As a fuzzing operator, I want a run of consecutive write failures reported once and the recovery reported once, so that a persistent problem does not flood the Simics log.
36. As a fuzzing operator, I want stats writing to resume automatically when the failure cause goes away, so that a brief lock does not disable stats for the rest of the campaign.
37. As a fuzzing operator, I want `fuzzer_setup` written once per session and describing the TSFFS configuration, so that `afl-whatsup` can discover the Instance and I can see how the campaign was set up.
38. As a fuzzing operator with coverage reporting enabled, I want the Branch target count reported as `tsffs_branch_targets` in `fuzzer_stats`, so that I keep the firmware reachability measure that `log.json` heartbeats used to carry.
39. As a fuzzing operator, I want `afl_version` to identify TSFFS and its version, so that tools and humans can tell a TSFFS Instance from an AFL++ one.
40. As a fuzzing operator, I want keys whose value TSFFS cannot know to be omitted rather than zero-filled, so that every value in the file is real.
41. As a TSFFS user, I want `log.json` to stop accumulating heartbeat and prose stats records, so that stats have a single, standard home.
42. As a TSFFS user, I want `log.json` to keep its interesting, solution, and timeout records for now, so that I lose no data until the AFL output layout replaces them.
43. As a TSFFS user, I want `heartbeat`, `heartbeat_interval`, `log_to_file`, and `log_path` documented as deprecated with their replacements, so that I can migrate my scripts.
44. As a TSFFS user, I want the documentation to describe the new attributes, the Instance layout, the `default` name and the Instance lock, and restart rotation, so that I can configure stats without reading source.
45. As a TSFFS user, I want the `log.json` documentation to state that it is deprecated and what replaces each record type, including where Branch target counts went, so that I can migrate before it is removed.
46. As a Windows user, I want a "Monitoring a campaign" guide that explains `afl-whatsup -d` (the PID liveness check does not work for Windows or remote Instances), `afl-plot` prerequisites (bash and gnuplot via WSL or Git Bash), loading `plot_data` in pandas or a spreadsheet, and that a stale `last_update` means a stuck iteration, so that I can monitor campaigns without AFL++ installed natively.
47. As a fuzzing researcher, I want `plot_data` to use the AFL++ 15-column layout, so that existing plotting scripts and notebooks work unmodified.
48. As a TSFFS maintainer, I want fuzzer-state-derived stats computed inside the fuzzer and live counters kept on the Simics side, so that each value comes from the component that actually knows it.
49. As a TSFFS maintainer, I want the stats stage's field names and computations to mirror upstream LibAFL's `AflStatsStage`, so that a future LibAFL upgrade can replace ours with upstream's.
50. As a TSFFS maintainer, I want the domain glossary to distinguish Edge from Branch target, so that future contributors do not conflate the two again.

## Implementation Decisions

- **Two producers, one writer.** A new LibAFL stage, `TsffsAflStatsStage`, runs last in the fuzzer's stage list and computes every value that requires the fuzzer `State`: `cycles_done` and `cycles_wo_finds` (scheduler metadata queue cycles), `pending_total` / `pending_favs` (scheduled count and favored metadata), `corpus_count`, `corpus_favored`, Edge count and `bitmap_cvg` (map feedback history map), `stability`, `cur_item`, and `max_depth`. It publishes these into a shared snapshot. The Simics side owns the live counters it already maintains (executions, crashes, timeouts, Branch targets, and the times of the last interesting, crash, and timeout events), merges them with the latest snapshot, and writes the Instance files.
- **Live corpus and Edge counts.** Between stage runs, the Simics side increments `corpus_count` for each `Interesting` message and adds its novel map indices to the Edge count. Each new stage snapshot overwrites both with the authoritative values from `State`.
- **Snapshot transport** is shared state guarded by a lock, not a channel message: only the latest snapshot matters, and the writer reads it on its own cadence. The snapshot holds counts only, never a copy of the history map, so lock hold times are limited to copying a small struct.
- **Stage structure.** The stage is a thin adapter that extracts raw inputs from `State` (history-map occupancy, unstable entry set, queue cycles, per-testcase scheduled and favored flags, current index, depths). All derivations (stability, coverage percentage, pending counts) are pure functions with no LibAFL types in their signatures.
- **Stage correctness.** Stability counts only unstable entries that are also filled history slots, so it can never go below 0%, and it reports 100% until calibration has produced unstable-entries metadata. `pending_favs` counts favored entries that are not yet scheduled; it does not reproduce the upstream 0.11 `corpus_size - favored` bug. The pending scan runs at most once per stats interval rather than every round. A missing current corpus index yields `cur_item` 0 instead of an error.
- **Why a stage and not a Monitor.** A LibAFL `Monitor` only sees events (aggregated execution counts, corpus size, objective count, user stats), never `State`, so it cannot provide cycles, pending, Edges, or stability. A stage alone runs only between fuzzing rounds, which can be minutes apart under Simics, so live counters stay on the Simics side. The `StatsMonitor` approach and its snapshot message are dropped.
- **Why not upgrade LibAFL.** The pinned revision (0.11.2) has an `AflStatsStage` that only fires a JSON user stat and writes no files. Newer revisions write files, but upgrading breaks every LibAFL API TSFFS uses, and an upstream stage would be just as stale between `fuzz_one` calls. TSFFS keeps its own stage, mirroring upstream field names and logic so it can be swapped out later.
- **Write cadence** is wall-clock driven on the Simics side, using the new `afl_stats_interval` attribute (seconds, default 10), checked on each simulation stop. One tick writes `fuzzer_stats`, appends a `plot_data` row, and prints the console status line. A final write happens at shutdown. If the simulation stops being reached (a wedged iteration), writes stop and `last_update` goes stale; this is documented as the "stuck" signal.
- **Console.** The stats writer prints the one-line status summary through the Simics log at each tick. The event manager keeps LibAFL's `SimpleMonitor` for new-testcase and objective lines, logged to the Simics console only, not to `log.json`. `maybe_report_progress` is not added, because it would still only fire between rounds.
- **Edge semantics.** `edges_found` and `bitmap_cvg` count Edges: occupied slots in the map feedback's history map. `total_edges` is the map size. Branch targets (the tracer's distinct program counters) never feed these keys; they are reported separately as `tsffs_branch_targets`, present only when coverage reporting is enabled.
- **Stability formula.** `(filled - unstable) / filled`, where `filled` is the number of occupied history-map slots and `unstable` is the number of those slots in calibration's unstable-entries metadata. `var_byte_count` is `unstable`. This deliberately differs from LibAFL's own `stability` user stat, which divides by the whole map size and therefore stays near 100%.
- **Crash/hang split** uses the Simics-side crash and timeout counters, since LibAFL stores both in one solutions corpus.
- **`fuzzer_stats` keys.** Lines are formatted as AFL++ does (`{key:<18}: {value}`); percentages as `%.2f%%`; timestamps as Unix seconds, with `0` for an event that has not happened. Keys: `start_time`, `last_update`, `run_time`, `fuzzer_pid` (the Simics process id), `cycles_done`, `cycles_wo_finds`, `time_wo_finds`, `execs_done`, `execs_per_sec`, `execs_ps_last_min`, `corpus_count`, `corpus_favored`, `corpus_found`, `max_depth`, `cur_item`, `pending_favs`, `pending_total`, `stability`, `bitmap_cvg`, `saved_crashes`, `saved_hangs`, `last_find`, `last_crash`, `last_hang`, `execs_since_crash`, `exec_timeout`, `edges_found`, `total_edges`, `var_byte_count`, `afl_banner` (the Instance name), `afl_version` (`tsffs-<version>`), `target_mode` (`tsffs`), `command_line` (the Simics command line), and `tsffs_branch_targets` when coverage reporting is on. AFL++ keys whose value TSFFS cannot know (for example `slowest_exec_ms`, `peak_rss_mb`, `corpus_imported`) are omitted, not zero-filled.
- **`fuzzer_setup` content.** Written once at session start: one `name=value` line per TSFFS configuration attribute, followed by a `# command line:` line with the Simics command line, matching the layout AFL++ uses so that `afl-whatsup` 4.x, which discovers Instances by finding `fuzzer_setup`, picks them up.
- **Configuration attributes** on the `tsffs` object: `afl_stats` (bool, default true), `afl_stats_interval` (seconds, default 10), `output_directory` (default: an `output` directory in the Simics project), and `instance_name` (default `default`). An `instance_name` that does not match `[A-Za-z0-9._-]+`, or that consists only of dots, is rejected at startup with an error naming the allowed characters.
- **Instance lock.** At session start TSFFS takes an exclusive OS file lock (`File::try_lock`) on `<instance>/.lock` and holds it for the session. If the lock is held, startup fails with an error stating that the Instance is in use and that parallel sessions need distinct `instance_name` values. The OS releases the lock when the process exits, so a crashed session never blocks the next one. The lock is taken before rotation, so a second session can never rotate a live session's `plot_data`.
- **Instance directory contents.** `fuzzer_stats` (rewritten on each write via write-to-temporary then rename), `plot_data` (AFL++ 15-column format with header, appended each write), `fuzzer_setup` (written once per session), and `.lock`. ADR 0001's next stage puts `queue/`, `crashes/`, and `hangs/` in this same directory.
- **Restart rotation.** At session start, after taking the lock, an existing `plot_data` in the Instance is renamed to `plot_data.<unix_timestamp>` and a fresh file with a header is started. A stale `fuzzer_stats` is simply replaced.
- **Error policy.** Stats write errors never propagate out of the simulation-stop handling. The writer keeps a single `failing` flag: the first failure after a success logs a warning naming the error; further failures log at debug level; the first success after a failure logs an informational recovery message. There is no immediate retry; the next tick is the retry. Startup errors (invalid name, Instance in use) are the exception and fail the session, because they are configuration mistakes rather than transient I/O.
- **`log.json` changes.** Heartbeat and prose message records are no longer written. Startup, interesting, solution, and timeout records are unchanged. `log_to_file` and `log_path` keep working. `heartbeat` and `heartbeat_interval` are accepted but no longer have any effect; the stats cadence is `afl_stats_interval`. All four are documented as deprecated; there is no runtime deprecation warning.
- **Documentation.** The configuration chapter documents the four new attributes, the Instance layout, the `default` name and the Instance lock, rotation, and the deprecated attributes with their replacements. The `log.json` section gains a deprecation notice pointing to ADR 0001's replacement plan, including that heartbeat Branch target counts moved to `tsffs_branch_targets`. A new "Monitoring a campaign" page covers `afl-whatsup -d`, `afl-plot` prerequisites, loading `plot_data` with pandas or a spreadsheet, and reading a stale `last_update` as a stuck iteration.
- **Format target.** Field names and file layouts track AFL++ 4.x/5.x as consumed by `afl-whatsup` and `afl-plot`.

## Testing Decisions

- **Good tests here assert on the files a user would read**, not on internal structures: the key set and values in `fuzzer_stats`, the header and column count of `plot_data`, the presence of rotated files, and the absence of removed `log.json` records.
- **Seam 1: the Instance writer (unit tests, no Simics).** Input: one merged stats record. Output: files in an Instance directory under a unique temporary directory per test. Cases: the full `fuzzer_stats` key set and value formatting, including omitted keys and `tsffs_branch_targets` present only when coverage reporting is on; the 15-column `plot_data` header and rows; `execs_ps_last_min` from actual elapsed time; rotation of an existing `plot_data` at session start; `fuzzer_setup` written only once; atomic replacement of `fuzzer_stats`; a second writer on a locked Instance failing with the in-use error, and a lock released by a dropped writer allowing the next; an injected I/O failure producing a warning instead of an error, a second failure not warning again, and recovery logged on the next successful write; rejection of invalid Instance names. These replace the existing writer test, which used a fixed temporary path and failed on re-runs.
- **Seam 2: the stage's pure derivation functions (unit tests).** Stability (including unstable entries outside the filled set, and no calibration data yet), coverage percentage, and pending counts, given plain inputs. No LibAFL `State` is constructed.
- **Seam 3: one end-to-end Simics integration test.** Modelled on the existing magic-harness integration tests (built on `simics_test::TestEnvSpec` with an iteration limit). It runs a short campaign with a fixed `instance_name` and asserts: `fuzzer_stats` parses; `edges_found > 0`; `corpus_count >= 1`; `execs_done` equals the iteration limit exactly (which verifies the final shutdown write); `plot_data` has a header and at least one row; `log.json` contains no heartbeat or message records. This is the only test that exercises `TsffsAflStatsStage`'s extraction from a real LibAFL `State`. Rotation is covered by Seam 1 only.
- **Build verification** includes the Windows GNU target (`x86_64-pc-windows-gnu`), since the default MSVC target does not link.

## Out of Scope

- An AFL output layout (`queue/`, `crashes/`, `hangs/`) replacing `log.json`'s interesting, solution, and timeout records. This is the next stage of ADR 0001; this spec only fixes its location (the Instance directory).
- Dumping the raw coverage bitmap (`map.afl` / `fuzz_bitmap`), including the choice of bitmap format and dump trigger.
- Cumulative or per-testcase drcov output for Lighthouse/IDA, and the final removal of `log.json`.
- Upgrading the pinned LibAFL revision.
- A bundled plotting script, a JSON-lines stats stream, a Prometheus endpoint, or a Simics `status` command.
- Separate cadences for `fuzzer_stats` and `plot_data`.
- Compatibility with tools that need a full AFL output layout or replay binaries (`afl-cmin`, `afl-tmin`, `afl-cov`, CASR, FuzzBench reporting).
- Resuming `plot_data` time series across sessions; TSFFS counters restart per session, so sessions are rotated instead.

## Further Notes

- This spec supersedes the first implementation on this branch, which used a custom LibAFL `Monitor`. Review of that version found that stats write errors could abort the Simics session, that coverage counted Branch targets against the map size (exceeding 100% on large targets and reading 0 with coverage reporting off), that the recent-speed figure divided by the configured interval rather than elapsed time, that stability and several timestamps were hard-coded, that writes were not atomic, and that parallel and restarted sessions corrupted each other's files.
- Review of an earlier revision of this spec against the original motivation found the console-freshness goal unaddressed, `corpus_count` staleness contradicting its user story, heartbeat attributes left with no meaning, and Branch target counts dropped with no replacement. This revision fixes all four, switches the default Instance name to `default` with a lock, and cuts the Windows rename retry, per-error-kind deduplication, and the history-map snapshot.
- `afl-whatsup` checks liveness with `kill -0 <fuzzer_pid>`, which cannot see a native Windows Simics process from WSL or Git Bash, nor a process on another host. Instances then show as dead; `afl-whatsup -d` includes them. This is documented rather than worked around.
- Vocabulary follows `CONTEXT.md` (Edge, Branch target, Instance). The `log.json` retirement plan is ADR 0001.
